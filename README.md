## 1. Что это?

Предположим у вас есть репозиторий, где хранятся какие-либо конфигурационные ямлики, например, манифесты.
Возможно, вам часто приходится заполнять одни и те же параметры в нескольких ямликах, предназначенных, например,
для разных стендов. Возможно даже, что конфигурация зависит от стороннего продукта, который достаточно часто обновляется.

manifestum-medicatus *(от лат. манифестовое волшебство)*  - это небольшой проект, который может сэкономить вам большое количество времени.
Он автоматизирует заполнение подобных конфигурационных файлов.

## 2. А как это работает?

Еще один хороший вопрос. Принцип работы предельно прост. У вас есть два ключевых элемнта:

1. Базовая конфигурация, определяющая, что вообще может находится в ямликах вместе с примерами параметров

2. Текущая конфигурация, определяющая то, что вы хотите внести в базовую от себя.

Мерджим первое и второе - получаем третий элемент - слитые конфиги, где все текущие перекрывают все в базовом, а все базовое, если оно не переопределно 
в текущих ямликах, остается нетронутым.

## 3. Пон, а в каких кейсах я могу это использовать ?

Что-ж, навскидку можно сходу выдать два:

1. У вас имеются в вашем любимом репозитори ваши текущие конфиги, однако проект, от которого они завиcят, обновился.
И теперь, чтобы не обновлять вручную конфиги для каждого стенда, вы просто переопределяете базовые конфиги и мерджите их с текущими.
И все.
2. А теперь представим, что вы решили поменять во всех текущих конфигах на всех стендах один параметр. Тогда в текущем манифесте надо переопределить этот самый параметр один раз, а скрипт наплодит
вам измененые конфиги для каждого стенда
3. Также в *base_manifests* можно вставить ваши *текущие* конфиги, а в *current_manifests* вставить дельта параметры - то, что вы хотели бы поменять

## 4. Как это работает под капотом?

Слияние происходит рекурсивно по следующим правилам:

- Если и в `base`, и в `current` — **словари** → мерджим по ключам.
- Если хотя бы один — **не словарь** (строка, число, список) → `current` **полностью заменяет** `base`.
- **Списки не сливаются**, а заменяются целиком (так задумано: примеры в `base` не должны попадать в прод).

### Умное удаление опциональных полей

Скрипт использует **схему опциональных полей** (`schemas/optional_fields.yaml`), в которой явно указано:
- какие **корневые секции** optional (например, `KAFKA`, `GRPC`, `FLUENT_BIT`),
- какие **поля внутри блоков** optional (например, `SECMAN.EGRESS_CUSTOM_CA_KV_PATH`),
- какие **корневые скалярные параметры** optional (например, `K8S_TYPE`, `SSM_CP`).

При запуске в режиме **`--type update`**:
- Все optional-секции и поля **автоматически удаляются из `base`** перед слиянием.
- Если вы **добавите** их в `current` — они появятся в результате.
- Если не добавите — их **не будет**, и Helm **не активирует** ненужную логику.

## 5. А как этим пользоваться?

В проекте есть три базовые директории:
1. base_manifests - здесь вы храните все (на данный момент 4) базовые манифесты
2. current_manifests - здесь хранятся все текущие манифесты, которые мы либо дополняем обновленнымы базовыми конфигами, либо из них плодим конфиги для других всех нужных стэндов (смотри пункт 3.2)
3. merged_manifests - здесь хранятся все смердженные манифесты. Для каждого вида монифеста присутствует своя папка. В каждлй такой папке - набор манифестов для каждого стенда

Когда вы вставили базовые конфиги (на 6.11.2025 там лежат базовые конифиги для aef) и текущие конфиги (также лежат актуальные на 6.11.2025) вам нужно закомментировать все параметры из base_manifests, которые вы не хотите видеть в 
merged_manifests. Однако, если это элементы из списка - не переживайте, список он просто возьмет из current_manifests (смотри пункт 4).
, то просто впишите слеудющу команду:

### ▶️ Запуск

```
# Режим по умолчанию: `reconf` — оставляет всё из base (для отладки)
python main.py -st DEV IFT1

# Режим `update` — удаляет опциональные поля (рекомендуется для продакшена)
python main.py -st DEV IFT1 -tp update

**Нужно указать минимум один стенд!**
```

После этого в папке merged_manifests, в каждой папке будут созданы смердженные манифесты с называнием стенда (посмотрите структуру папки и все станет ясно).
Также важно отметить, что все параметры, которых небыло в current_manifests, но были в base_manifests (и соответственно переписались в merged_manifests) выводятся в логи.

А на этом все, до скорых встреч.
